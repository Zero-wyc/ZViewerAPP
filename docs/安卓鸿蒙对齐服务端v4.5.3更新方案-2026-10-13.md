## 3. 默认音量对齐

### 3.1 字段与行为

服务端 `SystemSettings.roomDefaultMusicVolume` 为 0～100 的整数百分比，数据库默认 50，由 `/api/auth/public-settings` 下发，保存时服务端校验范围。它是全局配置的初始音乐音量，**不是需要房主向观众同步的房间播放状态**。

1. 客户端 `src/upstream/store/systemSettingsStore.ts` 补字段和 50 的默认值。现有接口使用对象展开，运行时可能已经接收额外字段，但播放器尚未读取，不能据此认定功能已对齐。
2. 增加 `src/upstream/modules/music/utils/volume.ts`，参考上游 `initialMusicVolume`：有效 `zc-music-volume`（0～1）优先；无记录、空串、非数值或越界记录使用服务器默认；老服务端缺字段时回退 50%。保留用户保存的 `0` 和 `1`，不强制把所有历史用户重置为 50%。
3. `useListenTogether.ts` 的初始化、惰性 audio 创建、预载升格和设置晚到场景都要使用同一音量。服务器请求失败不能回到 100%。本次已经手动调节过的音量不能被晚到的设置覆盖，即使本地存储写入失败。
4. 保留客户端已有 `settingsRevision`、`invalidate()` 清空默认状态和旧请求校验；不要用上游较简化的设置 store 整文件替换。当前 `src/App.tsx` 的 `persistSession()` 已重拉共享设置，`resetConnection()` 已使其失效，应沿用这条切服链。
5. 首页另有只读取 `roomCreationMode` 的 `loadPublicSettings()`，它不是音乐播放器设置 store。不要把默认音量仅放进这个首页局部状态。
6. 现有 `zc-music-volume` 沿用当前全局本地偏好语义；本轮不额外改变持久化 key。切服后默认配置需重新读取，旧服务器迟到响应不得写入新连接。

### 3.2 UI 边界

管理端滑条与整数编辑已在服务端网页实现，无需在 App 复制 AdminPage 或增加管理员接口入口。App 原有音量控件继续使用本地 0～1 值，显示百分比；保留已有触屏拖动锁滚动、pointercancel/卸载清理和主题样式。系统媒体音量与应用 audio 音量不是同一个数值，避免改写系统音量。

### 4.2 播放与权限规则

1. **仅房主推进共享 FM。** 一般播放器的 `canControl = isHost || hostOffline` 不足以授予 FM 推荐/入队权限，FM 页面和自动推进需额外判断 `isHost`。观众继续通过申请和广播同步；房主在线时观众自身 ended 不得重复添加下一首。
2. 首次进入 FM 页面只展示候选，用户启动播放后建立活动 FM 会话。自然结束和播放器「下一首」从新候选继续；候选不足补拉 DEFAULT 或 mode/submode 接口，模式无数据时沿用上游默认源回退。
3. `music:queue-upsert` 携带 `afterCurrent: true`，等待成功 ack，再播放并发出同步状态。入队拒绝/超时不提前修改当前歌曲、不丢候选、不假定已经成功；异步期间再次检查房间、房主身份和会话代次。
4. 排除当前曲目、候选内重复及回退历史中已播放歌曲；防止自然结束重播唯一当前曲。当前需求不是删除历史房间队列，保持已有队列语义，不擅自追加清理策略。
5. 显式选「单曲循环」仍循环当前曲；普通队列顺序/随机和 B站推荐续播走原有路径。上游 FM 会话未启用时不得截获普通网易云歌曲的下一首。
6. 切换 FM → 搜索/我的音乐/哔哩哔哩等页面，候选与播放器会话仍存活；选择普通歌曲/B站插播后停用 FM。离房、切服、断连及组件销毁取消旧请求。仅返回到 FM 页面不应自动抢播。
7. 页面重新挂载能够读回当前候选/歌曲/历史。这里的持续会话限于仍在当前房间的活跃播放器，不承诺 App 被杀、整页重载或房间重建后自动恢复无限漫游。
8. 自动切曲完成后封面、歌词、队列选中态、媒体 ID 和播放位置一起更新。快速手动选曲、下一首连点、补拉期间暂停、切模式和服务端返回旧响应，均不能触发过期曲目抢播。

### 4.3 双端已有逻辑必须保留

客户端 Hook 与上游有实际差异：`getEmbeddedProxyStatus()` / `subscribeEmbeddedProxy()`、账号及会话隔离的 `biliAudioCacheKey()`、`buildCliProxyUrl()` 和 `loadRequestRef` 均存在。直接覆盖 `useListenTogether.ts` 会丢掉本机 B站解析、私有音源地址和旧解析取消保护。

- 保留 `getApiUrl()`、`apiGet()`、`appendAuthToken()` 及客户端 `connectionTransport` 连接映射；FM 请求和音频仍走已选服务器与现有认证通道，不使用 ArkWeb 本地页面 origin 拼相对 API。
- 保留 `src/mobile/useMusicAudioRouting.ts` 的实际 playing 事件捕获，使预载元素升格后仍能恢复音乐路由；不能破坏语音活跃时的音频策略。
- 保留 `useMediaSessionSync()` → `src/mobile/useSystemMediaSession.ts` → `src/platform/mediaSession.ts`，系统「下一首」应调用同一个新增 FM 分支。不要用上游浏览器版 MediaSession Hook 覆盖双端原生会话、后台任务和歌词逻辑。
- 保留 Android/HarmonyOS 平台边界；网页共享业务可以统一，不能把 Android Java 或 HarmonyOS ArkTS 桥接搬进 FM 页面。
- 上游已有 ack 超时与错误提示不代表实际网络/登录失效能无限无缝续播。遇到音源或服务失败应有明确可恢复提示，不用静默单曲重播伪装成功。

### Android

`native/bilicore/core/wbi.go` 已在共享修复提交 `a8abd64` 更新重排、空格 `%20` 与特殊字符过滤，并有固定签名向量测试。现有维护记录明确发布的 1.7.5 APK 未重新构建。后续先跑 Go 测试，再生成 AAR；`ZV-Android/app/build.gradle` 的 `buildBilibiliCore` 以 Go 源码为输入、`libs/bilicore.aar` 为输出，并由 `preBuild` 依赖，正式构建时核对该任务实际执行。

### HarmonyOS

实际签名发生在 `ZV-HarmonyOS/entry/src/main/ets/services/BilibiliResolver.ets` 的 `signedPlayUrl()`，不会自动使用 Android Go 核心。需直接校正 ArkTS 表，使用相同固定向量，再核对 `query()` 的排序、UTF-8、空格百分号编码和过滤规则。中文搜索与 playurl 参数按实际调用链分别验证，不能只依据一个向量宣布全部搜索/播放都通过。仅运行 `harmony:web` 不会完成 ArkTS 修复，仍需编译并安装新 HAP。

1. 在指定客户端仓库合并默认音量工具/设置字段，保留切服请求代次；先验证新旧服务端与本地音量兼容。

3. 补客户端测试，修复并验证鸿蒙 WBI 实际路径；Android 纳入已有 Go 修复，核对 AAR 生成。
4. 更新 Android/HarmonyOS 维护文档，记录真实构建、设备场景和未覆盖项；按下一版实际版本同步 package/lockfile、Android Gradle、HarmonyOS AppScope。不要提前把规划标成已完成。
5. 运行共享验证、分别生成平台网页资源，再构建 Debug/Release、按既有签名流程校验与安装；成功完成版本构建后做本地 Git commit，发布另按发布准则办理。
