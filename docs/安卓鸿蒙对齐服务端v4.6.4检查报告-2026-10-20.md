## 3. P0：媒体库 HLS 基址冲突

### 服务端变化

`backend/src/routes/emby-like-factory.ts` 新增 `resolveHlsResource`、`validateHlsResource` 和 `rewriteHls`。`/api/emby|jellyfin/stream` 与挂载 `/proxy` 返回的清单，将分片、子清单和标签中的 `URI="..."` 改写为服务端接口，例如：

```text
/api/jellyfin/stream?movieId=4&resource=%2Femby%2FVideos%2Fitem%2Fhls1%2Fmain%2F0.ts
```

`resource` 限定到对应上游及影片目录，上游 `api_key` 等凭据由后端补入。客户端不应再把这些服务端接口当作上游 NAS 的相对文件。

### 客户端证据

- `src/upstream/modules/player/services/library-hls-proxy.ts` 按 movieId 调用 movie-source，取出 `directUrl` 并为旧服构建通用 `/api/stream/proxy` 方案。
- `src/upstream/modules/player/engines/hls-engine.ts:242` 无条件为媒体库 stream 解析这个 helper；`createProxyLoader` 成功回调把 `response.url/context.url` 恢复为 helper 的上游清单地址。
- 将新后端真实 `rewriteHls` 函数与客户端真实 loader/helper 接在一起，得到：清单基址为 `https://library.example`，上述子资源随之解析成 `https://library.example/api/jellyfin/stream?...`，下一次通用代理实际请求的也是这个错误上游路径；正确归属应是 `https://server.example/api/jellyfin/stream?...`。

该探针使用占位域名，没有访问真实媒体库，没有将测试向量视作设备实播。它已经确认 URL 组合错误，实际黑屏/解码表现仍需原生验收。

### 实施要求

1. 新服的媒体库清单由专用 `/stream|proxy` 端点管理，保留其逻辑服务端基址和 `resource` 参数；不要再对重写后的接口恢复上游 NAS 基址或套第二层通用代理。
2. 子清单、TS/fMP4、AES key、MAP 均按同一契约处理；保留 `movieId/ms/at`、当前成员鉴权和中止信号。
3. 保留 `connectionTransport` 的逻辑 URL/原生传输 URL 转换。反代路径前缀要单独测试：新版后端输出从 `/api/` 开始的路径，客户端仍需解析到用户所选服务端前缀。
4. 若继续兼容旧服，按能力或实际响应区分“后端已重写”和“旧服清单仍含上游资源”；不能直接删除旧服补救，也不能根据 `package.json=1.0.0` 判版本。
5. 不把上游媒体库凭据写入房间 store、片单、Socket 广播或日志；媒体 API 403 与 token 401 分开处理。

## 4. P0：主动断开后的 Socket 会话恢复

`backend/src/middleware/socket-auth.ts` 在连接时设置 token 到期定时器，主动 `socket.disconnect(true)`；账号改密/禁用等撤销事件也主动断开已有连接，并对后续数据包再次验证。HTTP 无效/撤销 token 统一返回 401，刷新接口也拒绝已撤销的登录用户 token。

客户端 `src/upstream/hooks/useSocket.ts` 的 `disconnect` 处理只更新 connected；刷新逻辑只接在 `connect_error`。本轮使用仓库已安装的真实 Socket.IO server/client，复现服务端相同的主动断开：

```json
{"reason":"io server disconnect","connected":false,"active":false,"connects":1,"connectErrors":0}
```

Socket.IO 在这种主动断开后不会自动重新连接，也不会产生握手错误让现有刷新逻辑执行。当前界面可能一直显示“正在重连”，房间信令、观影/音乐同步、审批及原生投屏信令随之停止。

实施时应区分传输断开、服务端主动断开、用户退出和切服：前两者走适当的有界恢复；用户退出/切服必须使旧恢复失效。服务端主动断开可先通过唯一 refresh 任务确认当前身份，成功后重新握手、重新准入；刷新被明确拒绝时清理房间媒体并返回认证入口，不能无限循环。网络失败保留身份并提供可重试状态。

现有 `useMobileRoom` 已在 `connect` 后执行 register-host/request-join；需要复用它，并验证新 socket 的房间 Session 真正恢复后才取资源。特别检查已有 `sessionExpired`、跨服身份守卫、旧 ack 作废和主动离房的取消逻辑，不新增旁路自动重登。

## 5. P1：删除旧直链中转字段和错误开关

新源码已从 `Movie` 实体、MovieDto、movie service、前端 store、提交器和 resolver 全链路移除 `directLinkProxy`。现在：

- 视频直链为 `directLink=true`，客户端直连，失败明确提示。
- WebDAV/OpenList 播放方式是“直链直连”或“服务器转发”；内网挂载由服务端强制转发。
- **`serverProxy` 仍存在，服务于 anime/ani-subs、Kazumi、CMS 等数据源；不能因为删除 directLinkProxy 就全部删掉。**

2.1.1 的 `MoviePushPanel.tsx:205` 把同一个 `serverProxy` 开关同时写入 `directLinkProxy/serverProxy`，底部开关又显示于 mp4 和多种挂载源；`roomStore.ts` 继续映射被删除字段，`movie-source-resolver.ts:549` 继续按它包装代理。

升级后，旧端新增影片的 directLinkProxy 不会被新服持久化，返回 DTO 又会被映射为 false，出现“开关已开启但没有按承诺中转”的问题。需定向清理 DTO、添加/编辑请求、恢复比较及 resolver 中的旧字段；调整开关显示范围和文案；挂载表单以真实的 directLink 二选一控制。历史字段不能被解释成无提示的网络策略迁移。

原生本机回环/证书通道仍是客户端连接层，不等于服务端转发，不能连同中转开关一起删除。HLS/DASH/MP4/playsvideo 的 `noProxyFallback` 决策必须一致。

## 6. P1：普通用户房主的片单权限

新后端 `modules/movie/movie.routes.ts`、`routes/rooms.ts` 的 `canControlRoom` 为 root 或正数 userId 对应的 room owner，不再限定 admin owner。排序接口也使用这项判断。

客户端 `src/upstream/modules/room/components/playlistOrder.ts:2` 仍是 root 或 admin owner；`MovieListPanel.tsx:131` 仅给 admin 调 `/api/admin/rooms` 读取 owner。对真实函数输入 role=user、userId=4、ownerId=4，本轮返回 false；admin owner 返回 true。新后端可用的普通房主排序会在客户端被隐藏或拦截。

应使用普通成员可读的房间资料/权威会话身份识别 owner，同步检查排序、清空、删除、修改及改名入口。不能用“当前观看角色 isHost”完全替代持久化 owner，也不能为了读 owner 让普通用户访问管理 API；转交播放房主时尤其需要区分两者。服务端继续最终鉴权，不把 manageMovie 的细粒度权限扩大成无条件 REST 管理权限。

## 7. 准入、403 和游客身份

新 `backend/src/services/room-access.ts` 以当前主房间 Session 判断读取权限，root/owner 有特定例外；影片列表、挂载 movie stream/movie-source/direct-resolve、字幕、弹幕数据及语音授权等相关入口已加检查。不能再假定“已登录且知道 movieId 就能读取”。

当前 MobileRoom 已在 `room.phase === 'ready'` 后挂载一起看播放器，`useMobileRoom.ready()` 后才读取弹幕，语音入口也受 ready 控制，**这部分已有基本顺序，不应误报为一定在准入前取片单**。仍需联测重连、切模式、等待审批、被踢和关房后的读取/取消；Socket 恢复只完成连接还不够。

`apiFetch` 已支持 `refreshAuth:'unauthorized'|'never'`，语音 token/mute/kick 已使用 unauthorized，无需重复开发。影片、媒体库和字幕调用仍有默认 403 刷新行为，建议对新准入端点使用 unauthorized，并将 403“请先通过房间准入验证”作为业务拒绝处理，按当前房间状态有界恢复，避免重复刷新 token 掩盖未准入。

游客 token/Session 新增 guestId，旧 `userId=0` 不再共享批准白名单；批准、拒绝必须对应真实 pendingRoomId，准入会再次原子检查容量。客户端通常仍把 token 当不透明凭据，不需在 ArkTS/Android 自行生成 guestId。验收旧游客凭据自动刷新、两个游客分别审批、断线重进是否重新审批；不得把所有游客 id=0 当同一个人。
