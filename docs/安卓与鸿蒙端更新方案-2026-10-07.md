## 3. P0：B 站大会员番剧/影视解析

### 3.1 应达到的行为

1. 支持 `ep123`、`ss123`、`/bangumi/play/ep...`、`/bangumi/play/ss...`，以及展开后指向这些地址的短链接；普通 BV、多 P 继续可用。
2. ss 先取得整季及可播放分集，再确定目标 ep；切集用目标 `epId` 和 `cid`，不能把番剧当作同 BV 的普通分 P。
3. 显示整季标题、集名、会员标记、当前集及试看状态。会员资格、地区限制、下架、凭据过期等给出可区分反馈。
4. 有效大会员且拥有该内容访问资格时验证完整播放；非会员按源站授权得到免费内容、试看或明确错误。不能把“解析成功”或接口报告的完整时长作为已获得完整正片的证明。
5. 内置代理按本机 B 站账号解析；服务端解析按服务端可用的房主身份解析。这两个身份必须在设计和测试中分别处理。

### 3.2 共享 TypeScript 数据链

上游依据：`backend/src/services/bilibili/{pgc,resolver,cache}.ts`、`backend/src/routes/stream/resolve.ts`、`frontend/src/modules/bilibili/`、`frontend/src/modules/room/components/{MoviePushPanel,MovieListPanel}.tsx`。

客户端修改入口：

**上游本身也有需要补核的接缝：**目标提交 `bilibiliApi.ts` 的 `mapResolvedBilibili()` 仍未拷贝顶层 `epId/seasonId/seasonTitle/preview`，尽管类型及后端已新增。这会让服务端返回字段在前端归一化时丢失；移植必须补齐，不能只复制类型。`pages` 已整体传递，不能因此误认为顶层试看标记也已保留。

### 3.3 Android 原生侧

当前 `native/bilicore/mobile/mobile.go` 的 `/resolve` 从 `bvid` 构造 `ResolveOptions`；`core/quality.go` 的移动解析围绕 BV 信息和 UGC playurl。仅替换上游前端或 Windows CLI 文件不能使 Android 获得 PGC 能力。

实施步骤：

1. 扩展 `native/bilicore/core/resolver.go` 的请求/返回结构；可将 PGC 信息获取与播放解析放入新增 `core/pgc.go`。
2. 对照上游 `pgc.ts` 接入 season 与 PGC playurl，处理不同响应包裹、ep/cid 对应、会员/地区错误、DASH 与 durl 回退。
3. 将 PGC 轨道送入现有普通画质筛选、设备编码能力选择、备用 CDN、autoMax/manual 与失败回退策略；不直接把最高 qn 当成设备可播放能力。
4. `/resolve` 支持明确的 ep/ss 参数或规范化 PGC URL，限制参数有效范围；响应与共享层定义一致。旧 BV 参数保持兼容。
5. `BilibiliProxyPlugin.java` 原则上继续管理启动/登录/状态；若需要能力标记，先扩展 `src/platform/contracts.ts`，不让 Java 承担房间业务。
6. 通过现有 `scripts/build-bilicore.mjs` 生成绑定及 AAR，之后执行网页同步和 Android 构建。

Cookie 留在 Go/原生侧，不返回 React、不加入 Socket、不上传为服务端房主 Cookie。PGC API 请求可使用本机凭据，CDN 媒体请求继续遵守凭据与域名边界。

### 3.4 HarmonyOS 原生侧

当前 `BilibiliResolver.ets` 只有 BV 信息、WBI UGC 播放解析；`BilibiliLocalProxy.ets:resolveEndpoint` 只读取 bvid/cid 等参数。

实施步骤：

1. 扩展 `ZV-HarmonyOS/entry/src/main/ets/services/BilibiliResolver.ets`，或拆出 PGC service；使用显式 ArkTS 类型定义季、集、轨道和错误结构。
2. 扩展 `BilibiliLocalProxy.ets` 的 `/resolve` 参数与返回值，语义与 Android 保持一致。
3. 保留 `BilibiliCredentialStore.ets` 的本机凭据存储、回环随机端口/路径、Origin/Host 校验、Range/HEAD、签名查询参数与备用 CDN。
4. 新增能力如需桥接，在 `contracts.ts → bridge-bootstrap.js → Index.ets/service` 同步扩展；单纯新增 HTTP `/resolve` 字段不必另加重复 JSBridge 方法。
5. PGC DASH 首选设备可解码轨道；既有 HEVC Main 10 限制不会因番剧解析支持而自动解除。

### 3.5 会员身份、时长和错误处理

- **本机代理模式**：使用每台设备自己的 B 站账号。房主大会员不意味着观众本机账号也能播放完整会员集。
- **服务端模式**：播放重解析传 `movieId`，后端查影片房间房主的服务端 Cookie；添加影片之前尚无 movieId 时沿用请求者身份。手机本地扫码不会自动为服务端提供 Cookie，不能承诺本机登录后服务器解析也有会员资格。
- `preview`、真实 durl 长度和最终播放器 duration 需要联合核对；上游以 badge/会员状态推断试看，应对限免、付费及异常返回补测试，不能把所有 badge 都等同于会员专享。
- 处理 `-403`、`-404`、`-10403` 等上游业务错误；不以绕过源站资格或地区限制作为目标。

## 4. P0/P1：仅 CLI、路由、默认设置和多 P

### 4.1 cliOnly 在手机端的语义

`Movie.cliOnly === true` 时，手机内置代理是本机 CLI 能力的等价承载，应使用 Android/鸿蒙本机代理，无需安装桌面 EXE或打开固定 `127.0.0.1:9333`。

- 补齐 DTO、store、新增/更新影片参数和共享解析器的 cliOnly 门控。
- 从解析、首次挂载、同步更新、重载、切画质、失败回退各入口执行约束；本机代理未就绪或 PGC 能力缺失时，不回退服务器媒体代理，不播放房主回环 URL。
- 将上游 `ViewerCliRequiredOverlay.tsx` 改造成移动端“登录 B 站 / 重启内置代理 / 重试”提示，按 `getEmbeddedProxyStatus` 及能力变化触发恢复。
- 失败或换片时清理阻塞标记；旧片的 cliOnly 状态不能阻塞下一部普通影片。
- 允许服务端元数据/同步请求；“服务器零媒体流量”指视频和音频流，不代表所有服务端请求为零。

### 4.2 媒体路由

在 `src/upstream/modules/player/services/url-proxy.ts` 增量合并上游 `platform=html5` 判断。已包装的本机代理 URL优先保留；PGC 防盗链 CDN 地址经本机或允许的服务端代理注入正确请求头。cliOnly 下禁止服务器媒体兜底。

上游曾尝试 no-referrer，随后已回滚；不要移植该中间提交。以本次固定提交的最终路由为依据。测试实际 206/Content-Range、音画推进及 seek，不把拿到 URL 视为播放通过。

### 4.3 默认解析模式

接入 `systemSettingsStore.ts` 中 `bilibiliDefaultParseMode`、`bilibiliPgcDefaultMode`，增加 parseOptions 的 `configured` 区分“没配置”和“明确选择 MP4”。新服务端通过公开设置下发这两个默认值，手机无须新增完整后台管理页。

建议手机策略优先级：影片 cliOnly 强制约束 → 用户显式影片配置/手动画质 → 已就绪且已登录的内置代理自动高画质 → 服务端普通视频/PGC 默认模式 → 旧服缺省 MP4。`dashDisabled` 仅约束服务器 DASH，不禁用本机 DASH。此顺序是保留现有移动能力后的适配决策，实施时写入测试，不能照搬桌面默认值覆盖本机策略。

### 4.4 多 P 与竞态

已有：观众覆盖校验 movie.cid、sessionVersion；缓存含 URL/cid/原生画质/能力；解析后验证当前影片与账号状态。

待补：服务端解析各调用点传 `page: movie.currentPage` 与 `movieId`；缓存增加 page 和解析身份维度；处理广播 state.cid 与影片 DTO 不同时到达，等待一致数据再解析，避免旧覆盖重挂。继续保留 generation/sessionVersion/画质 revision 等取消判断。回归普通 BV 多 P、番剧切 ep、快速连续切换、先状态后影片列表，以及房主/观众分别走本机和服务端的组合。

## 5. P0：不安全证书连接功能

### 5.1 产品行为与范围

主页增加“允许此服务器使用不受信任的证书”，默认关闭，属于每个服务器的连接设置；启用状态在连接信息中可见，并可撤销。覆盖用户提出的自签名、证书链不完整等兼容场景；过期、域名不匹配等错误须保留分类，便于明确例外实际覆盖范围。

这是用户提出的新增客户端功能，**不是本次上游已经实现的能力**。没有取得具体樱花穿透地址和失败日志，本次不能断言所有自动 HTTPS 的问题均由证书造成。受信任且域名正确的自动签发证书应直接连接；TLS、CORS、Mixed Content、WebSocket 转发和 LiveKit 媒体不可达应分别诊断。

建议以规范化 `scheme + host + port` 绑定原生策略；默认不扩展到任意域名、B 站 API/CDN或重定向后的外域。外置 LiveKit 若为独立地址，需独立的明确绑定，不继承为全局信任。例外只保存在当前应用，不修改系统证书库。

### 5.2 当前实现与方案入口

| 层次 | 当前源码依据 | 计划 |
| --- | --- | --- |
| 共享 UI | `src/App.tsx` 直接 fetch 登录/恢复，另有 `apiFetch` | 显示每服务器连接策略；应用策略完成后再探测、恢复或登录 |
| 平台契约 | `src/platform/contracts.ts` 尚无服务端信任能力 | 新增 `serverConnection.ts` 及最小契约，例如设置/撤销指定服务器策略、无凭据探测及错误分类；命名为方案建议 |
| Android | `MainActivity.java` 已自定义 `BridgeWebViewClient`，仅覆写页面完成事件 | 在既有 client 中整合处理与诊断，保留 Capacitor 资源加载、安全区和导航逻辑 |
| Android HTTP | Manifest 已 `usesCleartextTraffic=true`，Capacitor 已 `allowMixedContent=true` | 不把这两项当作证书兼容修复；验证 HTTPS 网络栈实际行为 |
| HarmonyOS | `Index.ets` 固定本地网页源、无 SSL 事件处理 | 增加原生策略 service 和 ArkWeb 错误回调；通过现有 bridge 请求链设置策略，不放开任意网页导航 |

Android 官方文档说明 SSL 错误回调仅处理可恢复错误，并建议默认取消；不能用无条件 `proceed()` 充当生产连接方案。应先验证限定服务器/证书的信任路径，严格保持默认验证；不可恢复握手错误仍返回明确失败。[Android WebViewClient 文档](https://developer.android.com/reference/android/webkit/WebViewClient#onReceivedSslError(android.webkit.WebView,%20android.webkit.SslErrorHandler,%20android.net.http.SslError))

ArkWeb 的 `onSslErrorEventReceive` 仅主资源，`onSslErrorEvent`（API 12+）支持主/子资源；本项目加载本地 HTML、跨域访问服务端，不能只加主页面回调。具体事件字段及可用能力还需以构建 SDK 和目标设备验证。[OpenHarmony 官方 ArkWeb 文档](https://github.com/openharmony/docs/blob/master/zh-cn/application-dev/reference/apis-arkweb/arkts-basic-components-web-events.md#onsslerrorevent12)

### 5.3 必须先完成的网络可行性验证

证书例外不能仅靠 React fetch 参数实现；也不能假定一次 WebView 回调放行会覆盖浏览器 WebSocket、原生下载及 WebRTC。先用隔离证书测试服务完成以下小型验证，再确定正式实现：

| 链路 | 验证内容 |
| --- | --- |
| HTTPS API | 无凭据探测、登录、令牌刷新、NDJSON、Cookie/Bearer 语义及错误返回 |
| Socket.IO | polling 与 WebSocket 升级均验证，切服/重连没有遗留旧连接 |
| 媒体 | 同源代理 MP4、DASH/HLS 请求、Range、字幕、封面及下载；外域默认验证不被削弱 |
| LiveKit | `/api/voice/token` 与返回 `url` 的 WSS 信令分别验证；同源和独立域名分别验证 |
| RTC 媒体 | ICE UDP/TCP 与 TURN/TLS 独立检查；HTTPS 例外不等于修复 UDP/TCP 端口或 TURN 证书 |
| 生命周期 | 关闭开关、切服、进程重启后策略一致；处理 WebView 可能缓存的 SSL 决策，撤销后不能继续意外放行 |

优先做原生按服务器/证书受限的信任处理；可恢复回调是否覆盖所有实际请求，以两端实验结果为准。若 WebSocket/媒体不受该机制覆盖，需补原生连接适配或受限本地转发，明确 HTTP 流式响应、WS 升级、Cookie、取消、Range 的代价和边界；不能只代理登录请求便宣布完工。不得采用进程级信任所有证书、全局关闭校验或 Chromium 全局忽略证书错误作为交付方式。

证书开关不修改 HTTP/HTTPS 选择策略；遇到证书错误时应优先显示可诊断原因及本服务器例外入口，不能偷偷改为 HTTP 并发送账号密码。受限例外方案能否覆盖目标设备全部链路，是本模块实施前的技术验证门槛，不是本轮已验证结论。

## 6. P0：主页 HTTPS 优先与完整地址模式

### 6.1 输入与选择规则

建议两种模式：“自动（优先 HTTPS）”和“自定义完整地址”。自动模式接收域名、IP、端口和可选路径；粘贴显式 `http://` 或 `https://` 时保留用户协议，可切为完整地址模式，不再次补前缀。

| 输入/情况 | 预期结果 |
| --- | --- |
| `example.com` | 先探测 `https://example.com`，符合回退条件时再探测 `http://example.com` |
| `192.168.1.10:3333` | 先 HTTPS 同端口，再 HTTP 同端口；不擅自改端口 |
| `[IPv6地址]:3333` | URL 解析保留方括号与端口，按同样顺序探测 |
| `https://example.com/zviewer/` | 保留协议和路径，去除末尾多余斜杠；不偷偷回退 HTTP |
| `http://example.com:3333` | 尊重显式 HTTP，按指定地址连接 |
| HTTPS 证书错误 | 显示证书问题及例外选项；自动模式也不将此类错误等同于未提供 HTTPS |
| HTTPS 明确未提供 TLS / 端口不可用 | 自动模式可继续无凭据 HTTP 探测，成功后展示实际选中 HTTP |
| 401/403、维护页、非 ZViewer JSON、CORS 错误 | 与协议可用性分开，不因业务错误盲目循环回退 |

### 6.2 实施顺序

1. 将 `src/mobile/serverUrl.ts` 拆为纯输入校验/候选地址生成与异步探测；不要让每次 render 中的同步 normalize 隐式发请求。
2. 统一 `src/upstream/lib/api.ts` 的 `ensureProtocol` 与主页策略，避免一处补 HTTPS、另一处重新补 HTTP。API、Socket、资源 URL 统一使用已经确定的完整地址。
3. 用现有 `/api/auth/public-settings` 等无鉴权 JSON 接口识别服务端；探测不带密码、Bearer 或旧 refresh token。校验 JSON 结构，不能只看状态 200。
4. 单次探测设置超时和取消；用户改地址或重复点击后旧结果不能覆盖新选择。原生探测成功后仍要在实际 WebView 请求链核验 CORS 与连接能力。
5. 自动模式按 HTTPS → HTTP 有序探测；分类所需错误由原生诊断补充，JS 的通用 TypeError 无法可靠区分证书、CORS 与断网。HTTP 命中后在登录前展示实际协议。
6. 检测完成后统一应用服务器地址、证书策略，再发起登录；保存最终完整 URL。恢复旧会话时沿用已保存协议，不自动把旧 HTTP 会话迁到新 HTTPS origin。
7. 切换服务器、协议或 base path，清理旧 auth/socket/settings/voice 与待处理请求；不能把旧服凭据试探性发给新服。
8. 自定义地址允许 path prefix，但 API 拼接、Socket.IO path、媒体 URL、LiveKit 反代是否支持该前缀必须联调；不能宣称 URL 语法支持就等于服务器支持任意部署路径。

地址选择建议与证书策略共用一个服务器连接设置模型；格式化、检测、保存、恢复只有一个最终地址来源。

## 7. P1：LiveKit 增量对齐

当前客户端 `useVoiceChat.ts` 已使用服务端返回的 `data.url/data.token` 连接，保留 generation、切服取消、麦克风清理与自动播放恢复。无需再迁移一次旧语音协议。

- 增量合并实际线路检测和 VoiceChatPanel UDP/TCP 徽标；检测依据选中 ICE candidate pair，不能把后台设置值当成当前实际线路。无法获取时显示未知/不显示，断连与重连时清空过期值。
- 上游读取 LiveKit SDK 内部 `pcManager`/`_pc`，需封装兼容检查，失败不得影响通话；核对当前锁定 SDK。TURN 情形如需解释实际传输，要结合候选类型/relay 信息，避免把徽标当作完整网络拓扑证据。
- 新上游 TCP 模式保留 UDP 并增加 ICE/TCP，默认 TCP 端口为 **3337**，可由 `LIVEKIT_RTC_TCP_PORT` 覆盖；不是强制全部走 TCP，也不应把历史 NAS 配置端口写死到客户端。
- 管理端切模式会重启嵌入式 LiveKit。当前客户端对最终 `Disconnected` 会执行 leave，不能仅凭服务端注释承诺自动恢复；测试 SDK 暂时重连与最终断开两条路径，必要时提供显式重新加入，并保留禁言/踢出语义。
- 新 `livekitExternalUrl` 优先于环境变量和请求头推导；手机继续消费 token 返回 URL，不能自己拼接或替换成主页域名。重入时重新取 token，外域证书策略单独适用。
- 服务端外网可达性自检只是诊断，不能把 HTTPS/WSS 正常视为 RTC 媒体已打通。

服务端依据：`backend/src/{entities/SystemSettings.ts,routes/admin.ts,routes/voice.routes.ts,services/livekit-server.manager.ts}` 与 Compose。手机不新增后台运维页面，仅消费相关行为和进行联调。
