## 4. 本次需要更新的客户端内容

### A. B 站影片关键词搜索（P1）

新增上游 `BiliSearchModal` 的移动端实现，接入 `MoviePushPanel` B 站来源输入框。支持关键词、分页追加、空结果/失败反馈、标题高亮标签清理、封面代理；选择结果后回填 BV 链接并自动解析，再沿用原有清晰度/分 P/添加流程。

- 接口复用 `searchBilibiliVideos` → `/api/stream/bilibili/search`；本次上游并未引入新的搜索后端接口。
- 将解析入口调整为可接收本次选择的 URL，避免 `setUrl()` 后立即解析读到旧输入。
- 保留现有本机 B 站解析、PGC、`cliOnly`、实际画质/编码能力选择和凭据隔离。搜索结果选择不能绕过这些约束，也不能照搬网页的桌面 CLI 或服务器兜底分支。
- `MobileRoom` 当前传给 `MoviePushPanel` 的 `isHost` 实际是 `canAdd`；新增搜索按钮应沿用添加权限，不误收紧为只有真实房主能搜索添加。
- 验收：连续换关键词时旧响应不覆盖新结果；翻页不重复提交；普通视频/多 P 选择后内容正确；本机未登录、无添加权限、服务端搜索错误均有明确反馈。

### B. 影片列表搜索与触屏排序（P1）

对齐展开片单的集中搜索和排序入口，保留紧凑片单与完整片单的分工。复用现有 `reorderMovies(roomId, orderedIds)` 和服务端广播。

- 上游是 HTML DragEvent / `dataTransfer` 鼠标拖拽。移动端需实现 Pointer/触屏拖拽，或提供明确的上移/下移操作；仅加 `draggable` 不能作为双端完成标准。
- 搜索过滤期间禁用排序，不能把可见子集当作完整片单提交；屏幕共享模式不启用。
- 排序 REST 接口为 `POST /api/rooms/:roomId/movies/reorder`，请求 `{ orderedIds }`。后端实际限制为 root 或房间创建者；这与一般 `manageMovie` 切片权限并不等价，移交后的房主也可能被拒绝。UI 和错误提示必须遵守真实权限。
- 如先本地预览顺序，提交失败必须恢复或重新读取权威片单；上游 `void reorderMovies(...)` 的简单调用不应原样作为移动端失败处理。
- 验收：长片单滚动与排序不冲突、重新进入后顺序保留、其他成员收到相同顺序、403/断网/同时删片时不留下虚假顺序。

### C. 房主自动连播（P1）

新增 `roomStore.autoContinueEnabled`、设置方法和完整片单中的开关。与上游保持：默认关闭、房间本地状态、不跨重启持久化、不向观众广播开关；房主在影片 ended 后按当前完整片单选择下一部，观众跟随播放事件，末尾提示且不循环。

- 在 `useWatchTogether` 挂接 ended，离房/切模式/播放器更换时清理旧监听；屏幕共享和预览源不触发片单连播。
- 通过现有 `play-movie` 流程和服务端确认切换，保留 1.7.1 的超时/失败反馈。不要先乐观切换当前影片就宣告下一部播放成功。
- 列表排序、删除或成员身份变化后读取最新状态；重复 ended 不得连跳两集。取消开关或房主转移后旧回调失效。
- 验收：MP4、HLS/Kazumi、B 站片单分别跑真实播完切换；验证新影片实际出帧、时间推进及观众同步，不能仅看片单高亮。后台与系统媒体控件一并回归。

### D. 弹幕连续添加与已添加标记（P1）

调整 `DanmakuSearchModal`：成功后保持打开，标记已添加集数并防止重复点击，允许继续添加其他集数或来源；失败仍可重试。保留现有弹幕导入大小限制、权限判断、持久化失败回滚和广播链路。

- 当前 trackId 使用 `${source}:${episode.id}`；标记至少沿用相同来源隔离，不能只用 episode.id，防止不同来源同 ID 误禁用。
- 以 `addTrack` 成功为准再标记；切房间、关闭后重开、删除已添加轨道时明确重置/同步行为。上游局部 Set 的“本次打开”注释不能替代实际生命周期处理。
- 结果列表和集数区分别滚动；去掉会覆盖固定高度的 flex 布局冲突，加载状态留在列表内部。
- 验收：连加两集窗口不消失、失败不标记成功、跨来源同 ID 可区分、重新打开状态合理、已授权观众与拒绝权限均正确。

### E. Emby/Jellyfin 海报墙（P1，依赖新服务端）

补齐 `imageTag`、`productionYear` 元数据，给共享媒体库浏览器增加列表/海报墙切换、年份、目录导航、懒加载、缺图占位及多选。Jellyfin 必须传 `imageApi='jellyfin'`；同步补齐其目录类型，避免仅 Emby 类型有字段。

- 新图片端点：`GET /api/emby/mounts/:id/image` 与 `GET /api/jellyfin/mounts/:id/image`，参数 `itemId`、`tag`、`maxWidth`；上游当前缺少 tag 返回 400，没有海报字段时显示占位。
- 图片路由位于 `authenticateToken` 之前，不要求给 `<img>` 拼接账号 Token。服务端用挂载凭据获取图片；客户端仅使用 browse 返回的图片元数据。
- 上游 `buildEmbyImageUrl` 返回 `/api/...` 相对路径。双端页面分别由本地 WebView/ArkWeb 加载，必须按 `getApiUrl()` 拼成当前服务器地址，并复用现有 `connectionTransport` 映射，支持用户所选 HTTP/HTTPS 和证书例外通道。不能误请求本地页面 origin，也不能把 Emby/Jellyfin 的 API Key 拼到图片 URL。
- release 中“tag 校验”在当前路由表现为检查非空并转交上游图片请求；不要把它写成已验证的强身份认证或本地哈希匹配。
- 兼容旧服务器：缺少新增字段或图片接口不可用时仍可用列表、浏览目录和添加影片；不强制升级才能打开原有媒体库。
- 验收：Emby 与 Jellyfin 分开测；HTTP、正常 HTTPS、已授权自签名通道；有图/无图/过期图；进入季与单集、多选和播放均正常。

### F. 二级面板布局、动画与设置滚动（P2，随以上功能完成）

对齐 B 站搜索、Kazumi/AniSubs、片单、弹幕、媒体挂载/服务端文件浏览的标题与开合动画；补可展开到视口的二级面板控制。涉及 `Modal`、`FullscreenOverlay` 及调用方。

- 桌面上游多处使用 624px 总高/532px 内容高，手机短横屏、软键盘弹出时不能直接固定照搬。应限制在可用视口和原生安全区内，保证标题、关闭按钮、主要操作可达，列表内部滚动。
- 网页全屏指“二级面板铺满可用视口”，需要与现有播放器全屏、旋转和系统沉浸式区分；原生返回按“退出面板全屏 → 关闭最上层面板 → 现有返回链”处理，不能直接离房。
- 番剧集数展开/收起可移植 grid 行高动画；新搜索/换源清理展开缓存，避免旧结果残留。
- 高级设置仅移植必要的高度/内部滚动修复。客户端 `SettingsPanel` 已有移动专用布局、字体/字幕返回层级和玻璃主题修复，不能被上游桌面侧栏整体替换。
- CLI 锁形图标/文案统一可顺带对齐 `BilibiliParseSettings` 和 `ViewerCliRequiredOverlay`，不改变客户端内置代理语义。
- 验收：双端竖屏/横屏、深浅主题、软键盘、快速开关、原生返回、播放器全屏中再打开二级面板；不截断、不横向溢出、不误关闭底层房间。

### 5.2 房主离开、关房和重开

新服务端在房主断开/离开后 10 分钟宽限期到期时读取 `autoDeleteInactiveRooms`：开启则关闭，关闭则保留；读取失败仍按旧行为关闭。不是客户端应新增的十分钟计时器。

- 客户端继续区分 `host-disconnected` 与 `room-closed`；离线不等于已关房，不能提前清理成关闭状态。房主回来后恢复同步，显式关房仍停止媒体和语音。
- 管理端新增 `/api/admin/rooms/:roomId/reopen`，root 可重开任意房间，admin 仅可重开自己创建的房间；仅 closed 可重开。当前移动 App 没有对应 AdminPage，本轮不新增管理后台页面。
- 重开将 status 改回 active，不恢复关房时已清掉的播放记忆。客户端刷新列表/重新加入应成功，不承诺自动续播旧进度，也不假设存在新的“重开”推送事件。
- “移除无人的房间”及纳入已关闭房间的清理、管理卡片按钮不溢出，均由服务端管理网页提供；无需加入双端 UI。回归管理员清理后客户端列表/加入错误是否正确即可。

## 7. 双端实施边界与顺序

1. 先保留并回归 1.7.1 与新服务端兼容基线，再改共享功能。所有客户端源码和 Git 操作在指定 `ZViewer-client` 仓库完成。
2. 共享开发建议顺序：B 站搜索 → 片单触屏排序/自动连播 → 弹幕连续添加 → 海报墙；二级面板适配随各功能完成，不另起全量网页替换。
3. 共享代码写在 `src/upstream/`，移动壳/返回行为在 `src/mobile/`；平台能力只经 `src/platform/`。本轮未发现上游要求修改 Android Go 或 HarmonyOS ArkTS 解析协议，不为纯 UI 更新无故改原生核心。
4. Android 保留 Capacitor/Go 本机代理、音频路由、系统媒体会话、WindowInsets；HarmonyOS 保留 ArkWeb、zviewerNative、原生安全存储、AVSession/后台任务及原生安全区。
5. 实现后运行现有 `npm run test:adaptation`、`npm run test:media` 和 `npm run build`；为自动连播、排序失败恢复、来源隔离和海报连接映射补针对性测试。仅原生解析/连接有改动时追加相应 Go/ArkTS 验证。
6. 分别执行 `npm run android:sync` 与 `npm run harmony:web`，再构建 Android/HarmonyOS 安装包。`rawfile/web` 和 Android 网页产物由脚本生成，不手改生成文件。
