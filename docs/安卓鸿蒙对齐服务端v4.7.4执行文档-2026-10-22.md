### 3.3 来源、权限与默认值

| 场景 | 服务器中转 | 浏览器转码 | 行为 |
| --- | --- | --- | --- |
| `anime` / `kazumi` / `cms` | 显示，读写 `serverProxy` | 显示，读写 `playsvideoEnabled` | 当前影片保存后即时应用；其他影片下次播放应用 |
| MP4 直链、WebDAV/OpenList/Emby/Jellyfin 等非 B站源 | 不显示此通用中转按钮 | 显示 | 挂载路由继续使用其 `directLink`，不改成 `serverProxy` |
| B站 | 不显示 | 不显示 | 沿用独立 B站解析、账号与本机画质逻辑 |
| 屏幕共享模式 | 隐藏影片运行时设置 | 隐藏影片运行时设置 | 不触发播放设置写入 |
| 观众、无对应编辑权限用户 | 显示当前值但不可写 | 显示当前值但不可写 | 不能依赖“按钮变灰”替代服务端鉴权 |

- 新添加草稿保持当前客户端默认：`serverProxy=false`、`playsvideoEnabled=false`；B站添加路径维持自己的既有值。UI 改版不顺便改变默认播放策略。
- 读取旧影片时，`serverProxy` 仅明确 `true` 才开启；缺省 `playsvideoEnabled` 按现有 DTO 兼容规则视为开启。不能用 `value || true` 吞掉明确的 `false`。
- 运行时策略是影片/房间权威设置；本机 B站画质/CLI 覆盖仍限本机。不能将运行时按钮存成设备全局 localStorage 偏好。

## 4. A01–A02：保存与即时播放事务

### 4.1 API 契约

使用现有接口，不新增服务端协议：

```http
PUT /api/rooms/:roomId/movies/:movieId
Content-Type: application/json

{"serverProxy": true}
```

或只提交 `{"playsvideoEnabled": false}`。每次发送被操作的最小字段，不连带回写过期 URL、headers、画质或整个影片对象。

服务端成功返回 `{ success: true, movie: updated }`，并广播 **`movie-list`**。没有名为 `updateMovie` 的 Socket 请求事件；`updateMovie` 是客户端 store 方法名。

当前客户端 `roomStore.ts:412–455` 的更新参数缺 `playsvideoEnabled`，`682–699` 的响应只读取 success/message、丢弃 movie。须补可选字段及返回影片映射，保留现有调用方可忽略返回值的兼容性。

### 4.2 推荐事务顺序

1. 捕获 `server/roomId + roomSessionRevision + movieId + operationSeq`；按影片限制并发写入，保存期间禁用该影片两个按钮。
2. 发送最小 PUT。HTTP 失败、403/404/5xx 或无法确认成功时不提前重载、不广播新播放状态。
3. 确认当前会话仍匹配后，消费权威 `movie` 响应并映射到对应影片；若兼容响应不含 movie，则取得匹配的新片单后再应用。不能假定 Socket 一定比 HTTP 先到。
4. `movie-list` 到达后做幂等合并；同一确认值不能再触发第二次重载。旧房间/旧请求结果不能覆盖当前会话。旧快照与新响应冲突时按事务序号/确认值协调，必要时重新取权威片单，不凭网络到达顺序猜测。
5. 非当前影片至此结束。当前影片且仍具广播权限时，进入非 B站源重解析/重挂载事务。
6. 从新影片数据构造策略，保存当前进度、倍速与用户播放/暂停意图，复用现有串行加载与取消保护。新解析结果同时携带 `playsvideoEnabled`、`noProxyFallback`。
7. attach 成功并确认会话有效后恢复进度和意图，记录“已应用策略”，发布一次正常播放状态；观众沿用现有串行接收路径。

服务器实现先广播再返回 HTTP，不代表两个通道在客户端按同一顺序交付；这项竞态必须测试。

`operationSeq` 只能判断本机任务的新旧，不能作为未携带版本号的 `movie-list` 的服务器版本。广播与本次确认值冲突时，结合已确认字段并重新读取权威片单，不凭本机序号丢弃合法远端变化。

### 4.3 播放状态与失败处理

- 当前影片同 URL、仅策略变化也必须真实重挂载；同 URL 同策略不重复 attach。
- 继续使用客户端已有 `source-identity.ts`、`usePlayerSource` 串行队列与加载代次，不整文件覆盖为上游更简单的 URL＋两标志去重。
- 保存 `currentTime / playbackRate / 播放或暂停意图`；加载期间用户新触发的暂停优先于开始时的 `!video.paused` 快照。禁止重载完成后自行恢复用户已暂停的音频。
- 切片、删片、离房、换服、身份撤销和新的加载操作都使旧事务失效；旧事务的 finally 不能解除新事务的忙状态。
- **保存成功与播放成功分别记录**。本方案采用“保留已保存的新设置＋明确应用失败＋可重试”，不自动发送反向 PUT。播放失败时停止失败会话并暂停，保留上次成功快照；不得将新策略广播为已经成功播放，也不得偷偷播放旧源却显示切换成功。
- 若仍是当前有效房主，失败暂停应使用上次成功的播放快照发送正常暂停控制/状态（`isPlaying=false`），让观众和服务端停止按旧播放状态走时；不要广播失败的新源或假装新策略已应用。已离房、换房或失去广播权限的旧事务不得再发送任何状态。
- 用户重试使用已保存的新影片数据；用户主动切回则发新的最小 PUT。HTTP 超时但服务端可能已经保存时，应刷新权威值后再判断，不盲目本地回滚。
- 重载清理旧媒体引擎、下载、事件和音轨，不出现双声、残留网络流或进度条永久归零。

## 5. A03：解析、URL 与观众同步

### 5.1 ani-subs 的明确遗漏

客户端 `movie-source-resolver.ts:408–433` 的 `resolveAnimeOnline` 已返回 `noProxyFallback`，但遗漏 `playsvideoEnabled`；随后 `useWatchTogether.ts:1020` 的 `!== false` 将缺省当作开启。

在该返回分支补 `playsvideoEnabled: movie.playsvideoEnabled !== false`，同时核对初次播放、运行时重载、恢复和观众重解析。验收重点：**影片明确关闭转码时，不得在解析后重新变成 true**。

### 5.2 Kazumi 新旧影片记录

当前客户端只在 `sourceType === 'kazumi' && movie.sourceMeta` 时重解析；没有 sourceMeta 的旧记录走通用 URL 分支，不能正确消费新 `serverProxy`。重解析失败也缺少新版的存量 URL 回退。

按上游 `resolveKazumiOnline` 的语义补独立分支：

1. 保留现有 Kazumi `sourceMeta` 结构 `{ sourceId, episode, originalTitle }`；`episode` 包含 `id / title / episodeNumber / playbackParams`，当前没有必需的 `kind` 字段。沿用添加时保存方式，有完整元数据时实时解析。
2. 对旧记录或重解析失败，检查 recovery URL 与影片保存 URL；回退只接受真实 HTTP(S) 媒体 URL 或已识别的服务端代理 URL。当前新添加流程可能保存 `kazumi://source/episode` 占位地址，它只能用于标识影片，不能直接播放或套进代理；找不到有效媒体 URL 时明确报告解析失败。识别已保存的 `/api/stream/kazumi/proxy`，解出原源 URL 及需要的请求头。
3. `serverProxy=true` 时按当前服务重新包装；`false` 时还原直连源 URL。不能对已经代理的 URL 再套一层代理。
4. 保留 Referer、User-Agent、Origin、Cookie 等已有必要头；不能把 ZViewer 登录 token/cookie 当成源站头转发。
5. 始终返回片级转码值与对称的 `noProxyFallback`。无头信息、源签名过期或确实不可达时仍可失败，提示重解析/重新添加，不承诺旧 URL 必定能恢复。

### 5.3 代理 URL 的正确基准

ani-subs 已使用相对代理 URL；Kazumi 和 CMS 的现有 helper 仍可能把添加者的服务 origin 固定进媒体地址。

- 定向复用 `buildAntileechProxyUrl(..., { force: true, relative: true })`，不再造相同工具。
- 修改 `modules/kazumi/api.ts`、`modules/cms/api.ts` 的相关媒体代理构造，并核对添加、播放、恢复和分享状态的消费者。
- 相对 URL 最终必须由**本机所选 ZViewer 服务器**解析，不能落到 Capacitor/ArkWeb 本地网页 origin。
- 保留 `connectionUrl`、`logicalConnectionUrl`、`player/services/url-proxy.ts` 的证书例外通道和鉴权边界；不能将全部 API 请求粗暴改为相对地址。
- 媒体地址沿用 `appendAuthToken()` → `authenticatedMediaUrl(logicalConnectionUrl(getApiUrl()), ...)` → `connectionUrl()` 的实际入口（`player/services/url-proxy.ts:194–197`、`src/mobile/serverUrl.ts:27–37`）。不要使用 `new URL(relative, window.location.origin)` 绕开所选服务器与路径前缀。
- 验证同一房间房主使用内网入口、观众使用公网入口时，两端各自走本机所选入口；不固定使用添加影片那台设备的 origin，不产生代理循环。

### 5.4 观众必须处理两个方向

`useVideoSource.ts:471–480` 已对“状态要求直连、旧片单仍为中转”进行覆盖。反方向“状态要求中转、旧片单仍为直连”也要对称处理。

限于 anime/Kazumi/CMS：当播放状态给出明确 `noProxyFallback` 时，在独立重解析前以该权威策略协调影片副本；缺省仍按现有同源兼容逻辑。也可等待对应权威片单，但不能用旧片单重解析后再仅覆盖布尔字段、留下路由与标志不一致。

复用 `restoreStateSnapshot`、媒体身份比较及 `useViewerStateSync`，同时验证 `true → false` 与 `false → true`。不要把心跳变成另一个无条件换源入口。

### 5.5 服务端持久化边界

服务端实时播放状态能透传扩展字段，但本次核查的播放快照数据库存储包含 `noProxyFallback`，未完整持久化 `playsvideoEnabled`；影片表本身保存该开关。

正式影片在服务重启/恢复时，应从最新 Movie 补足明确的片级策略，不能因播放快照缺字段默认为 true。无对应 Movie 的临时预览缺少这一补足来源，应单列“服务重启后预览转码策略恢复”限制及测试结果。若需要服务端修复，另行在服务端仓库提出 PR；本客户端任务不修改 NAS 数据库。
