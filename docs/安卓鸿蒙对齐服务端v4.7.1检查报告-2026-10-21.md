# Android / HarmonyOS 对齐服务端 v4.7.1 检查报告

> 后续实施：本报告保留升级前检查结论；2.1.5 已按本报告修复并完成双端模拟器验收，详见 [实施与验证记录](client-2.1.5-validation.md)。

日期：2026-10-21（Asia/Shanghai）。本次已更新本地服务端源码，并对当前双端 2.1.4 做增量检查。**客户端程序尚未按本报告修改，没有构建或发布新版本。**

## 1. 结论

当前双端已包含上一轮 v4.6.4 对齐和跨来源播放快照修复，不需要重做整套适配。当前日常使用的数据源批量添加、片单解析及直连策略广播已有实现；本次确认的主要差距是：

1. **P1：相同播放 URL 的直连策略改变时，观众不会重新加载媒体引擎；请求状态应答还会被跳过。**
2. **P2：“访问模式”统计仍只看 `mp4/directLink`，数据源关闭中转后可能实际直连、界面却显示“服务器中转”。**
3. **P2：遗留预览链路缺少中转/转码策略透传，当前选集界面并未调用这条旧链路，应在清理或重新启用时处理。**
4. **P2：直连失败提示仍面向挂载源，需按数据源场景调整文案。**

上游 main 新增的 B站“首次解析补 CID”修复主要针对外部 CLI。Android Go、HarmonyOS ArkTS 内置解析均已自行获取视频信息并选取 CID，且共享层已支持 CLI `error` 字段；不能把网页文件差异直接判成双端首次解析缺陷。

本轮没有发现必须先完成才能连接新版服务端的新增 P0 协议迁移；上述结论来自源码、现有回归及本地定向探针，不代表两端已经完成新版服务端真机验收。

## 4. P1：相同 URL 的策略变化未重新生效

### 服务端契约

上游 [PR #23](https://github.com/Zero-wyc/ZViewer/pull/23) 已合入 v4.7.1：

- `backend/src/entities/PlaybackState.ts:94` 新增可空 `noProxyFallback`。
- `playback-memory.service.ts:352` 保存、`:507` 恢复该字段；使用 `??` 保留明确的 false，不把“中转”误当成缺省。
- 预览载荷及同步 DTO 声明相同策略字段。
- 网页端 `useViewerStateSync` 在源变化判断中加入 `previous.noProxyFallback !== state.noProxyFallback`；请求状态时，只有 URL 与策略均相同才跳过。

可核对 [上游策略判断](https://github.com/Zero-wyc/ZViewer/blob/fe55ddebedb91a4834d6752c5619ea75efec0bbd/frontend/src/modules/sync-playback/hooks/useViewerStateSync.ts)、[上游请求状态](https://github.com/Zero-wyc/ZViewer/blob/fe55ddebedb91a4834d6752c5619ea75efec0bbd/frontend/src/modules/playback-memory/hooks/usePlaybackStateRequest.ts)。

### 客户端差距与复现

| 位置 | 当前行为 | 实际探针结果 |
| --- | --- | --- |
| `src/upstream/modules/sync-playback/hooks/useViewerStateSync.ts:289`、`:295` | 仅按 `sourceUrl` 判断重新 attach；外层分流和内部执行均遗漏策略比较 | 同 URL，策略 false → true：store 变为 true，但 `applySourceToVideo` 调用 **0 次** |
| `src/upstream/modules/playback-memory/hooks/usePlaybackStateRequest.ts:111` | 同 URL 直接 return，发生在应用新状态之前 | 同 URL，应答策略 true、原状态 false：策略仍为 false，attach **0 次** |

这会影响同一媒体 URL 的策略修正、重新同步或恢复：状态中的策略与已创建的 loader/媒体引擎可能不同。探针直接执行当前两个真实 Hook 的事件/ack 回调，使用占位 URL 和替代媒体元素；确认的是控制流缺口，未测量真实播放流量或设备解码表现。

### 建议实施

1. 将 `noProxyFallback` 纳入已应用媒体身份，或至少同时修复广播外层分流、串行队列内部判断和请求状态跳过条件。只改其中一个判断不能保证重新 attach。
2. 比较“已成功应用的策略”而非刚写入 store 的策略，避免队列中先覆盖状态后丢失变化；保持现有串行切片、取消、旧会话失效及进度恢复逻辑。
3. 保留 true / false / 缺省三态语义，以及同源旧发送端缺省策略兼容。`playsvideoEnabled` 也影响引擎选择，应在同一轮验证同 URL 开关变化，避免仅验证 URL 更换。
4. 不把服务器心跳改成另一条无条件换源通道。移动端现有心跳仅校正当前媒体，迟到旧源必须继续被拒绝。

验收：同 URL 策略双向切换各重新加载一次，保持当前时间、暂停/倍速；相同 URL 与相同策略不重复加载。覆盖广播、请求 ack、队列处理中再次改变策略、切房/离房后的迟到应答。

## 5. P2：访问模式统计与真实数据源策略不一致

`src/upstream/modules/room/watch-together/WatchTogetherCore.tsx:127` 仍按“mp4 为直链，否则 `movie.directLink`”计算，并在 `:2005` 传给统计组件。`VideoStatsMenu.tsx:665` 将 false 显示为“服务器中转”，复制统计文本时同样使用该值。

anime/Kazumi/CMS 的中转由 `serverProxy` 决定，通常没有 `directLink=true`。真实片单 resolver 的 9 组探针已确认直连策略；从现有 Core 提取的真实 selector 对三种关闭中转的数据源均返回 false，因此显示错误，不应据此判断媒体真的经过服务端。

建议在共享业务层引入与上游 [media-policy.ts](https://github.com/Zero-wyc/ZViewer/blob/fe55ddebedb91a4834d6752c5619ea75efec0bbd/frontend/src/modules/movie-source/media-policy.ts) 同义的判断：

- 数据源读取 `serverProxy`，挂载读取 `directLink`；实际 `/api/stream/.../proxy` URL 优先判为中转。
- 对预览/尚未取得 currentMovie 的情况，参考实际状态 `noProxyFallback`，不强依赖片单条目。
- 更新统计显示与复制文本；本机证书通道和 B站回环代理不等于 ZViewer 服务端媒体中转，保持原生连接层边界。
- Core 还把 `currentMovieDirectLink` 用于 WebDAV/OpenList 内嵌字幕（`:196`）。修改时单独核对该消费者，不能只为统计正确而改变挂载字幕的回退权限。

验收：anime/Kazumi/CMS 中转开关两态、MP4、WebDAV/OpenList 直链、已解析代理 URL 的显示与请求路由一致；第三方源不携带所选服务器 token。

## 6. P2：遗留预览分支，先区分是否可达

旧代码的缺口仍存在：

- `MoviePushPanel.tsx:475`、`:548` 的旧单集处理函数仍用 `needsAniSubsProxy/needsKazumiProxy` 自动决策，未读取开关；Kazumi 旧单集还固化解析 URL，没有保存 `sourceMeta`。
- `roomStore.ts:201` 的 `PreviewPlayRequest`、`useWatchTogether.ts:1327` 的 `previewPlay` 未声明/写入 `noProxyFallback`。
- `useWatchTogether.ts:1385` 的预览广播未传 `playsvideoEnabled/noProxyFallback`；`:414` 的观众专用事件接收同样未消费两者。完整 state 广播已有转码字段，专用预览事件则会再次应用不完整状态。

**当前不能把这些直接写成日常选集播放故障。** 虽然旧函数仍作为 `onSelectEpisode` 属性传入 selector，实际 `AnimeSourceBrowser.tsx:37` 未接收该属性，`:158` 只调用 `onSelectEpisodes`；CMS 也统一批量加入片单。本轮已检查整个可执行函数，未发现单集回调调用，当前正常入口走第 3 节已验证路径。

建议优先删除未使用的单集预览回调及失效属性，或在保留/开放预览前贯通两项策略，并改为按开关选择代理、保存 Kazumi 元数据。不得为了跟随网页文件结构而把移动端批量选集改回立即播放。

若需要支持网页房主专用预览事件 → App 观众，仍需补齐接收端字段并实际联测；本轮没有证明该跨端预览链路已通过。

## 7. P2：直连错误提示应覆盖数据源

`player/engines/direct-route.ts:139` 和 `playsvideo-engine.ts:323` 仍提示“挂载源站”“重新保存挂载”“关闭挂载直链”。当数据源禁止中转后直连失败，这些指引与实际入口不一致。可借鉴上游改为“源站/源地址”，按来源指引开启服务器中转或检查 HTTPS/跨域。

保留 `direct-route.ts:129` 的 `isNativeRuntime()` 判断。普通 HTTPS 网页的混合内容限制不能直接作为 Android/HarmonyOS 原生连接通道必然失败的结论；改提示不应收紧原生可用的 HTTP/证书例外路径。
